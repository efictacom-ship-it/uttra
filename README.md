# نظام محاسبة ومخزون — مكتبة/قرطاسية

نظام محاسبي ومخزني متكامل (Laravel + Inertia/React) مبني حول مستند موحّد
(`documents` + `document_lines`) لكل أنواع الحركة التجارية: بيع، مرتجع بيع،
شراء، مرتجع شراء، مصروف، رصيد افتتاحي، تسوية مخزون، استهلاك خامات. كل ترحيل
يُنتج قيدًا محاسبيًا متوازنًا في نفس المعاملة، ولا يوجد عمود "رصيد" مخزَّن يُصدَّق
بمعزل عن الحركة التي أنتجته.

## المكوّنات المبنية

| الوحدة | الحالة | ملاحظات |
|---|---|---|
| الإعداد الأولي (Setup Wizard) | مكتمل | بيانات المنشأة، الشجرة المحاسبية الافتراضية، ربط الحسابات، الفترة الأولى، المستخدم الأول |
| الكتالوج (أصناف/وحدات/خدمات) | مكتمل | وحدة أساسية إلزامية بمعامل 1، وصفات استهلاك للخدمات |
| المشتريات | مكتمل | فاتورة شراء + **مرتجع شراء** (بتكلفة الشراء الأصلية، مع حساب فرق تكلفة) |
| المبيعات/الكاشير | مكتمل | سلة معلقة (مسودة) → ترحيل بعدة وسائل دفع + **مرتجع بيع** |
| المخزون | مكتمل | أرصدة بالمتوسط المرجح، حركات، رصيد افتتاحي، تسويات، **الجرد الدوري** (تجميد + فروقات) |
| المالية | مكتمل | سندات قبض/صرف/تحويل مستقلة، **صناديق الكاشير** (فتح/إغلاق بفرق موثّق)، **المصروفات** |
| الفترات المحاسبية | مكتمل | إقفال يرفض وجود مسودات داخل الفترة، وإعادة فتح موثّقة |
| التقارير | مكتمل (Backend) | مبيعات، مخزون، أعمار ذمم، تسوية حسابات، ميزان مراجعة، أستاذ عام، دخل، ميزانية، ضريبة، حالة الفوترة الإلكترونية |
| الفوترة الإلكترونية | **محاكاة (Mock) فقط** | راجع قسم "الفوترة الإلكترونية" أدناه — لا اتصال حقيقي بأي جهة خارجية |
| واجهات React/Inertia | جزئي | صفحات الإعداد/الكتالوج/الشراء/الأطراف/المخزون مبنية؛ بقية الشاشات (كاشير، تقارير، فوترة إلكترونية) تعمل بالكامل من الخادم (routes + controllers + services مُختبرة) بانتظار واجهاتها |

## التشغيل محليًا

```bash
composer install
npm install
cp .env.example .env
php artisan key:generate

# أنشئ قاعدتي بيانات فارغتين: DB_DATABASE و DB_DATABASE بلاحقة _test لملف phpunit.xml
php artisan migrate

npm run dev        # يشغّل Vite لواجهات React
php artisan serve  # أو systemd/`php artisan octane` في الإنتاج
```

أول زيارة تُحوَّل تلقائيًا إلى `/setup`: أنشئ المستخدم الأول (مالك)، بيانات
المنشأة (الاسم، الرقم الضريبي إن وُجد)، ثم اعتمد الشجرة المحاسبية الافتراضية
وأكمل ربط الحسابات المطلوبة (`AccountResolver::CATALOG`) قبل إتمام الإعداد —
لا يمكن الترحيل بحساب غير مربوط.

## تشغيل الاختبارات

```bash
php artisan test
```

الاختبارات (`tests/Feature`, `tests/Integration`) تغطي: محرك الترحيل (شراء/بيع/
مرتجعات)، قواعد الكتالوج، الجرد الدوري والتجميد، الكاشير والصناديق والمصروفات،
إقفال الفترات، التقارير، وطبقة الفوترة الإلكترونية بأكملها. تعمل على قاعدة MySQL
منفصلة (`DB_CONNECTION=mysql_admin`, `DB_DATABASE=..._test` في `phpunit.xml`)
حتى لا تلمس قاعدة التطوير.

## الرصيد الافتتاحي عند بدء استخدام النظام

عند الانتقال من نظام قديم أو من دفاتر يدوية:

1. أكمل الإعداد الأولي وأنشئ الفترة المحاسبية التي يقع فيها تاريخ البدء.
2. لكل صنف مخزني، من **المخزون → الأرصدة الافتتاحية**: أدخل الكمية والتكلفة
   الفعلية (متوسط تكلفة الشراء وقت البدء، وليس سعر البيع). يُنشئ هذا مستند
   `stock_opening` يقيّد المخزون مقابل حساب "الأرصدة الافتتاحية"
   (`opening_balance`)، ثم يجب ترحيل قيد يدوي يُقفل ذلك الحساب على حقوق
   الملكية الافتتاحية من شاشة القيود (خارج نطاق هذا الإصدار الآلي).
3. أرصدة العملاء/الموردين الافتتاحية: تُسجَّل كسندات قبض/صرف "دفعة مقدمة" غير
   مخصصة إن كانت أرصدة دائنة لهم، أو عبر فواتير افتتاحية مبسطة إذا كانت مدينة
   — لا يوجد اليوم مسار آلي مخصص "لترحيل الأرصدة الافتتاحية للعملاء دفعة واحدة"؛
   يُنصح بإدخالها فاتورة فاتورة أو بقيد يدوي موثّق بوضوح في `notes`.
4. تحقّق دائمًا بعد الإدخال عبر **تقرير ميزان المراجعة** (`/reports/trial-balance`)
   أن مجموع المدين = مجموع الدائن قبل بدء الترحيل اليومي.

## النسخ الاحتياطي والاستعادة

القاعدة MySQL هي مصدر الحقيقة الوحيد (لا حالة مهمة خارجها عدا ملفات المرفقات
تحت `storage/app`). نسخ احتياطي دوري:

```bash
# نسخ احتياطي (بنية + بيانات)
mysqldump --single-transaction --routines --triggers \
  -u stationery_admin -p stationery > backup_$(date +%F).sql

# استعادة على قاعدة فارغة
mysql -u stationery_admin -p stationery_new < backup_2026-09-30.sql
```

نسخ احتياطي لملفات المرفقات (`attachments.storage_key`) تحت `storage/app`
يجب أن يرافق نسخة القاعدة دائمًا بنفس التاريخ، وإلا فقدت الروابط معناها.
لا تُنسخ جداول `sessions`/`cache`/`jobs` احتياطيًا — تُعاد تلقائيًا عند التشغيل.

## الفوترة الإلكترونية — طبقة محاكاة (Mock) فقط

**تحذير صريح:** كل ما بُني في `app/Modules/EInvoicing/*` هو **محاكاة محلية
بالكامل** لدورة حياة الفوترة الإلكترونية (توليد → إرسال → قبول/رفض/انقطاع →
إعادة محاولة)، وليس تكاملًا فعليًا مع منصة فاتورة (ZATCA) أو أي جهة رسمية:

- **لا اتصال شبكي حقيقي**: `MockEInvoicingProvider` (خلف واجهة
  `EInvoicingProvider`) يُقرّر القبول/الرفض محليًا فقط، ولا يستدعي أي رابط خارجي.
- **لا شهادات ولا مفاتيح حقيقية**: `einvoice_devices.credentials_secret_ref`
  حقل مرجعي فارغ في هذه النسخة؛ لا توجد شهادة CSID ولا onboarding فعلي.
- **التجزئة والـ QR محليان**: `invoice_hash`/`qr_payload` في
  `EInvoiceGenerationService` تمثيل مبسّط، وليسا خوارزمية ZATCA المعتمدة.
- **جدول الصادر (outbox)**: كل توليد يكتب صفًا في `outbox_jobs`، ويُعالج يدويًا
  عبر `POST /einvoicing/outbox/process` أو بجدولة Uttra لاستدعاء نفس الرابط —
  لا يوجد عامل طابور حقيقي (Redis/SQS) في هذه النسخة.
- **نتيجة "غير معروفة" ليست رفضًا**: `connection_error`/`unknown` تُبقي
  المستند معلّقًا لإعادة المحاولة (`POST /einvoicing/{id}/retry`) على نفس
  السجل ونفس `document_id` الأصلي — لا إبطال تلقائي لأي فاتورة ولا تحرير حجز
  مخزون بناءً على نتيجة غير مؤكدة.

### لربط مزوّد حقيقي لاحقًا

1. نفّذ `App\Modules\EInvoicing\Contracts\EInvoicingProvider` بصف جديد يتصل
   فعليًا بمنصة فاتورة (تسجيل الجهاز، توقيع XML، الإرسال عبر HTTPS بشهادة
   العميل).
2. بدّل الربط في `AppServiceProvider::register()` من
   `MockEInvoicingProvider::class` إلى الصف الجديد.
3. احفظ الشهادة والمفتاح الخاص في خزنة أسرار حقيقية (**ليس** في القاعدة ولا في
   الكود)، واجعل `credentials_secret_ref` مرجعًا لاسم السر فقط.
4. لا تُبقِ `MockEInvoicingProvider` مفعّلة في بيئة إنتاج تتعامل مع فواتير
   حقيقية خاضعة لالتزام الفوترة الإلكترونية.

## ما يحتاج بيانات أو مفاتيح حقيقية قبل الإنتاج

- **الفوترة الإلكترونية**: مزوّد حقيقي + شهادة جهاز من منصة فاتورة (راجع القسم
  أعلاه). حاليًا يعمل بمحاكاة فقط.
- **بوابات الدفع/الشبكة**: لا تكامل فعلي مع مزوّد شبكة (مدى/فيزا) في هذا
  الإصدار؛ `financial_accounts.kind = card_clearing` حساب محاسبي فقط بانتظار
  تسوية يدوية أو ربط مزوّد لاحقًا.
- **البريد/الإشعارات**: `MAIL_MAILER` في `.env` غير مضبوط على مزوّد حقيقي.
- **بيانات المنشأة الحقيقية**: الرقم الضريبي، الاسم القانوني، الشعار — تُدخل من
  شاشة الإعداد، ولا قيمة افتراضية صالحة للإنتاج.
- **كلمات مرور قاعدة البيانات**: `stationery_app`/`stationery_admin` في `.env`
  يجب توليدها من جديد في كل بيئة، ولا تُستخدم القيم التطويرية في الإنتاج.

## بنية المشروع

راجع `docs/schema_changes.md` لتفاصيل الفروق بين تصميم القاعدة المستلم
(`docs/reference/stationery_schema.sql`) والتنفيذ الفعلي في `database/migrations`،
وقواعد التطبيق التي لا يضمنها SQL وحده (توازن القيود، عدم تداخل الفترات، سقف
المرتجعات، تجميد الجرد).
